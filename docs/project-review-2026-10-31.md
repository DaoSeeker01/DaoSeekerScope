## 已确认的问题

静态与动态收集器原先只在调用 backend 前检查上下文。如果最后一个 backend 在调用期间触发取消，随后返回错误，收集器可能将其合并为 `BackendFailure`，没有保留实际的取消状态。调用方等待和 backend 返回存在时序差异，因此不能依赖外层等待循环一定先看到取消。

新增两个直接调用内部收集器的测试，排除线程时序干扰。修改生产逻辑前，两项均确定失败：实际得到 `BackendFailure`，期望为 `Cancelled`。原始本机日志保留在 `target/cancellation-before-fix.log`，不是成功证据。

## 修复与回归

每次 backend 返回后，包括错误或被捕获的 panic，先重新检查上下文，再处理字段或 backend 错误。未取消、未超时的请求继续沿用原有失败隔离规则；取消与超时不会被本次 backend 错误覆盖。此检查不能强行终止仍在阻塞的原生调用，既有调用方等待上限和 worker 数量上限不变。

除两项确定复现测试外，新增一项公共 API 回归，分别覆盖静态阶段和动态阶段取消：失败请求不发布能力变化、不提交静态缓存；使用新 token 重试会重读静态信息，成功后动态刷新仍复用缓存。正常 backend 故障和已有超时/并发回归继续执行。
